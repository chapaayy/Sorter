# AGENTS.md — правила разработки OUTDOOR PhotoSorter (beta)

## Единая версия

1. **`main`** — стабильная основа, не изменять её в ходе этапов распознавания рекламы. Рабочая экспериментальная ветка **`feature/ad-recognition`** создана от актуального `main`. Установка нового тестового VPS — из этой ветки. Не создавать второй сайт, второй frontend или отдельный репозиторий; перенос изменений в `main` только после отдельного разрешения владельца.
2. Единственный пользовательский интерфейс — Vue 3/TypeScript в `PhotoSorter/frontend/src/`, обслуживается из Vite `dist` на **`/`**. Не возвращать `frontend/static`, `/v3/`, `/vN/` или второй frontend runtime. Deep links должны работать через безопасный SPA fallback. API остаётся `/api/*`.
3. Проект в бета-тестировании, однако это **не** разрешение произвольно удалять файлы пользователя на сервере. Любой полный сброс PostgreSQL/Models/SAM/ФО требует отдельного явного поручения, точных целевых путей и остановки служб. Изменение Git-кода не должно изменять данные само по себе.

## Замороженная математика MegaLoc

4. Не изменять `PhotoSorter/backend/app/recognition/`, порядок **ФО → группировка → SAM**, модель, скоринг, выбор верхнего кандидата и порог `0.50` без отдельного разрешения и сопоставимого реального regression baseline.
5. Не смешивать служебные WebP/кэши загрузчиков и постоянный reference embeddings cache с оригиналами. Не перезаписывать фото, не менять SAM и результаты уже опубликованного запуска скрыто.
6. Один MegaLoc Worker обрабатывает одно задание по блокировке PostgreSQL; сохранение прогресса, остановка, перезапуск и очередь должны отражать реальные состояния БД.

## Модульность и совместимость

7. HTTP endpoints — `server/api/routes/`; бизнес-правила — `server/services/`; SQL — `server/db/`; файлы и hardlinks — `server/storage/`; worker loops — `server/workers/` и `server/worker.py`; model inference — `app/recognition/`.
8. Одна функция/ответственность на модуль, не создавать большие файлы со смешанными обязанностями. Отсутствие второй UI не означает удаление совместимых backend HTTP endpoint, нужных текущему Vue или прежним данным.
9. Актуализировать `README.md`, `AGENTS.md`, `PROJECT_MAP.md`, `FILE_INDEX.md` и затронутую эксплуатационную документацию при изменении архитектуры. Не создавать пустых модулей ради структуры.
10. Миграции PostgreSQL только версионированные, аддитивные и согласованные с реальными схемами. Не регенерировать действующие секреты в `.env.generated`; не выводить пароли в логи. Сохранять Caddy TLS volumes.

## Данные и безопасность

11. Хранение: `Models/models/` и `Models/cache/` отдельно, `PhotoSorter/data/` отдельно, PostgreSQL в named volume. Никакие из этих каталогов и секреты не добавлять в Git.
12. Hardlinks допускаются только при общей ФС и неизменности оригинала; безопасная копия при невозможности hardlink. Hardlink и локальный ZIP — **не** бэкап.
13. Загруженные ФО и SAM — недоверенные input. Проверять расширение/размер/пиксели/контрольные суммы, UUID, доступ к owner-owned path; пресекать traversal/symlinks/ZIP Slip.
14. API чувствительных действий требует существующую сессию, CSRF/Origin-проверки. Авторизация должна одинаково работать на frontend, API, cookie HTTPS и под мобильным Safari.
15. Удаление партии — только по trusted DB identifiers, с учётом выполняющихся jobs и скачиваний. Постоянные образцы и модели не относятся к партии. Автоочистка назначается для новых успешных запусков после атомарной публикации ZIP. Срок настраивается от минуты, по умолчанию 2 месяца; уже назначенные дедлайны не пересчитываются. Ручной DELETE действует независимо.
16. Ограничивать объём журналов и очередь; не блокировать API обработкой больших изображений; оригинал отдавать viewer только по запросу.

## GitHub / CI / релизы

17. Новая функциональность поиска экранов и распознавания рекламы, документация и рефакторинг — **только `feature/ad-recognition`**. Запрещены коммиты, force-push и слияния в `main` без отдельной команды. Сначала анализ кода, затем коммиты и обязательные проверки. После каждого этапа остановиться и отчитаться.
18. Для новых партий проверка загрузки основывается на зарегистрированном серверном манифесте UUID/путей/размеров, не на `pending=0`. Старые партии без манифеста не объявлять завершёнными. Автообработка включается только при явном opt-in новой манифестной партии; общая настройка по умолчанию выключена. Единственный источник заданий — существующая PostgreSQL очередь и общий транзакционный enqueue; никаких браузерных автоповторов и повторных запусков после терминального job.
19. В интерфейсе ФО статус MegaLoc — только из PostgreSQL `jobs.status` и snapshot прогресса; `thumbnail_state` не считать успехом сортировки. Цвет успеха только для `completed`; предыдущие результаты оставлять доступными после повторной обработки. Для очереди и остановки — только существующие `/api/runs`, без новых UI-only состояний и удаления истории.
20. Единственный актуальный workflow — `.github/workflows/ci.yml` (backend/PG restore/frontend/browser/Docker runtime). Исторические названия отдельных `test_stageN_*.py` **не** означают наличие старых версий: это сохранённые регрессионные тесты, не удалять их ради названия.
21. После изменения UI запускать TypeScript build, Vitest и Playwright; после backend — compile/pytest и интеграционные проверки. Реальные 189/1315 ФО — отдельная приёмка, тестовые заглушки её не заменяют.
22. Никакой автоматической установки на реальный VPS и массового удаления данных через GitHub CI. Перед опасными операциями — независимый защищённый backup, восстановление на пустом стенде, проверка, явное подтверждение владельца. При бета-экспериментах не выдавать успешный CI за полную проверку всех сценариев.
23. Отдельной вкладки «Обработка» нет: подробности находятся в «Очереди», параметры в «Настройках». Запуск и повторную обработку делать только через ФО; без второй UI-формы. Для мониторинга использовать существующий `/api/runs` с `scope=active|history`, не опрашивать весь архив каждые 4 секунды. Ручные VPN-проверки и проверка на VPS обязательны отдельно от CI.

## Текущая архитектура — без переключателей

- **Это бета-тест**, а не production. VPS/БД/кэш и тестовые ФО на VPS можно сбросить
  при явном желании владельца: исходные наборы он хранит на собственном ПК.
  Не вносить защитные fallback-ветки ради старых установок.
- Единственный планировщик: `db/repositories/work_queue.py`; Worker:
  `server/worker.py`. Очередь объединяет ФО и подготовку образцов.
  Код старых очередей не возвращать.
- Единственный приём образцов: `/api/reference-imports` через
  `server/services/reference_imports.py`, `reference_uploads.py`
  и `storage/reference_objects.py`. Нельзя возвращать
  `kind=reference` в `/api/uploads`.
- `uploads.py` отвечает только за ФО. `services/reference_publication.py`
  атомарно публикует версии; MegaLoc берёт исключительно pinned manifest;
  `reference_gallery.py` хранит лишь представление готовых файлов.
- Изменения образцов не изменяют результаты прежних запусков. Удаление
  публикует новую версию, а исходные immutable объекты для истории сохраняются.
- Структура: один файл — одна задача; нет дублирующих API, постоянных
  flags/режимов и версий UI. При удалении/перемещении модулей сразу обновлять
  `FILE_INDEX.md`, `PROJECT_MAP.md`, тесты и инструкции.
- Проверять не только старые unit/e2e, но и fresh DB + первый импорт + FIFO
  `ФО → подготовка → ФО`, конкуренцию, восстановление, кривые/дублирующиеся
  фото, abort, версию на claim и браузеры Chromium/WebKit.


## Правила компактных задач и ETA

Карточки ФО, Очереди и Результатов используют **один**
`frontend/src/components/ui/CompactTaskCard.vue`. Стили локализованы в
`frontend/src/styles/task-cards.css`, ETA — в `utils/queueEstimates.ts`.
Нельзя опять размножать в каждом экране отдельную CSS-систему.
Отображать `overall_percent` только если его прислал MegaLoc;
не подменять процент общего прогресса прогрессом отдельного этапа.
Оставшееся время работающей ФО — только из измеренного backend ETA.
Для ожидающих суммировать все предшествующие задачи единой FIFO и
использовать реальные длительности прошлых ФО / подготовок с нормализацией
по числу фотографий. Если измерений нет или предшествующая задача
неизвестна/заблокирована — показывать «Время уточняется» вместо числа.
В результатах фактическую длительность рассчитывать из timestamp начала
и завершения. Проверять оба цветовых режима, desktop/mobile и tests/e2e.


## Текущие UI и скачивание

- **Один** источник статуса задачи: общий FIFO. Старый `ProcessingView`
  удалён. Подробности перенесены в `features/queue/RunDetail.vue`,
  настройки модели — в небольшие `features/settings/*.vue`.
- Загрузка ФО и образцов монтируется единожды через `UploadCenter.vue`
  внутри `Shell`; перенос между вкладками не отменяет загрузку.
  Повторный выбор папки после полного reload обязателен из-за ограничений
  браузерного API файлов.
- `ReferenceLibrary.vue` на десктопе занимает доступный viewport;
  галерея и список SAM прокручиваются раздельно. Виртуализация
  должна измерять именно scroll container, не слепо `window.scrollY`.
- Активные задачи и история — два режима одного `QueueView`, без
  огромных пустых плашек. Прогресс и ETA сохраняют один источник.
- ZIP: `services/archives.py` формирует immutable ZIP в каталоге результатов,
  `api/routes/downloads.py` выдаёт `FileResponse` с поддержкой Range;
  не возвращать zipstream или вторую параллельную загрузку.
- CPU потоки сохраняются `services/compute_settings.py`, применяются
  только перед следующей FIFO-задачей; **нет** веб-доступа к Docker socket
  и динамической смены cgroup.
- Тесты: ZIP reuse + bad path, CPU setting, light/dark, минимизация
  загрузки и FIFO, две прокрутки, большой ZIP и Range/206.

### Автоматический ZIP и хранение (новая схема)

- `server/services/archive_pipeline.py` создаёт полный ZIP перед статусом `completed`; `services/archives.py` публикует атомарно. `services/archive_retries.py` повторяет только архив, без запуска MegaLoc.
- Автоудаление после ZIP применяется только к новым готовым партиям; уже записанные `delete_after_at` при обновлении политики не пересчитываются. Полное удаление папки запуска включает `.archives`.
- `server/services/compute_settings.py` хранит отдельные CPU потоки ФО/образцов. Docker socket веб-приложению не предоставляется.


## Экспериментальный этап 2 — XFeat CPU

- Признаки рамки вычисляются официальной XFeat из закреплённой версии исходников и весов. Скачивание — только явной командой `--install`; inference читает только проверенные локальные файлы.
- Любой поиск экрана допускает **только** Образцы SAM, уже назначенной MegaLoc. Для неизвестной SAM или отсутствующей разметки не выдавать координаты. Перед признанием совпадения обязательны MAGSAC, несколько поддержанных сторон, проверки ошибок и формы.
- На этапе 2 ручной анализ завершённого run через CLI, без нового планировщика. Сохраняет результаты отдельно в `outputs/<run-id>/screen_search`; ZIP и `jobs.status` не трогать. Автоматическая FIFO-интеграция только на этапе 4.
- При оценке этапа обязательно реальное CPU inference и отдельная проверка на **реальных пользовательских ФО**. Синтетические тесты не подтверждают полевую точность поиска.


## Этап 3: DINOv2 и PaddleOCR — правила

- Новые рекламные макеты принадлежат `ad_layouts`, **не** библиотеке
  `reference_constructions` и не являются ракурсами Образцов.
- Классификация запускается отдельно по завершённому MegaLoc run
  **после** этапа 2 и **только** для XFeat `status=found`.
  `DINOv2 ViT-S/14` выбирает ближайший макет по cosine-score;
  `PP-OCRv5` русский проверяет слова, **никогда** не подменяет выбор
  DINOv2. Сомнения должны оставаться в JSON/API/UX.
- Не менять FIFO, `jobs.status`, ZIP и группировку MegaLoc до этапа 4.
- Модель DINO — проверенная локальная safetensors по SHA-256,
  только `--install-dino` выполняет сеть. PaddleOCR — CPU,
  отдельный `--install-ocr`, запуск на локальных моделях.
- Не объявлять модель «точной» по синтетическому CPU smoke; проверить
  реальные LED-фото и юридические условия конкретных pretrained-весов.


## Интегрированный этап 4 — обязательные архитектурные ограничения

- Ветка `feature/ad-recognition` остаётся тестовой; `main` нельзя
  менять или объединять без явного запроса. Режим рекламы — **opt-in**,
  `processing_settings.ad_pipeline_enabled` default false.
- Единственный `work_queue` и единственный CPU worker. Не вводить
  параллельный анализ, дополнительную очередь, /v3, новые приложения
  или вторую ZIP-подсистему.
- В `work_queue.claim_next` зафиксированы `ad_pipeline.annotations/layouts`
  и версии моделей. Встроенный этап использует ТОЛЬКО snapshot,
  никогда live-лист из БД. Поиск XFeat строго внутри MegaLoc SAM;
  слабые совпадения не назначать. OCR — только верификация.
- `ServerJob.finalize_results` запускает стадии до `build_for_job`;
  `completed` допустим лишь после атомарной CRC-проверки ZIP.
  Использовать ровно общий `archive_pipeline.selections` и для
  скачивания, и для ZIP-only retry — никакой скрытой пересортировки.
- Лучшие снимки — одно фото на `SAM + физический экран + макет`,
  пересвет/смаз оцениваются внутри экранной области. Сомнительные
  отдельно `Review_required`, неопределённые не считать успехом.
  Score качества не является модельной вероятностью.
- Глобальная библиотека макетов не удаляется с ФО. Система очистки
  удаляет всё внутри единого `outputs/RUN_ID`, вместе с ZIP.
  Существующие этапы не ломать. Ручные stage2/3 CLI запрещены
  для интегрированных запусков.
