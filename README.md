# OUTDOOR PhotoSorter

**Бета · один сайт · стабильная основа `main` · экспериментальная ветка `feature/ad-recognition`.** Приватная система сортировки фотоотчётов наружной рекламы по конструкциям. Сейчас используется одна модель MegaLoc: она сначала группирует фотографии ФО (порог по умолчанию **0.50**), затем сопоставляет группы с общей библиотекой образцов SAM. Нейросетевая математика не меняется при переработке интерфейса.

## Одна актуальная версия

- Сайт: `https://<DOMAIN>/` — **Vue 3 + TypeScript**, без `/v3/` и параллельного старого интерфейса.
- Страницы: `/fo`, `/references`, `/queue`, `/results`, `/logs`, `/settings`. Подробности запуска: `/queue/runs/:runId`. Вход: `/login`.
- API: `/api/*` на том же домене. Данные и авторизация остаются на сервере.
- Для системы разметки экранов разработка идёт **только в `feature/ad-recognition`**. `main` остаётся стабильной основой, слияние — только после отдельного разрешения владельца.
- `PhotoSorter/frontend/static/` удалён. Единственный frontend — `PhotoSorter/frontend/src/`; результат сборки находится в игнорируемом `dist/`.

## Установка на новый пустой сервер

Linux x86-64, Docker Engine + Compose v2, Python 3, собственный домен с DNS на сервер, доступные TCP 80/443. Целевая конфигурация: 8 vCPU (доступность CPU IDs 0–6), около 24 ГБ RAM и 200 ГБ диска. Указанные CPU — настройки, а не гарантия скорости обработки.

```bash
git clone --branch main --single-branch https://github.com/chapaayy/Sorter.git
cd Sorter
cp .env.example .env
nano .env            # DOMAIN=ваш-настоящий-домен
bash ./install.sh --deploy
docker compose --env-file .env --env-file .env.generated ps
```

**Примечание:** на пустой установке `--deploy` сгенерирует секреты; `--check` предназначен для проверки уже настроенного окружения. Логин `admin`, пароль сохранён в приватном `.env.generated`, который нельзя удалять или добавлять в Git. Модель/веса можно загрузить из веб-интерфейса.

В результате поднимаются `caddy` (HTTPS), `postgres`, `api`, `worker` (MegaLoc), `thumbnail` (WebP) и `cleanup` (служебная очистка). Снаружи публикуются только 80/443.

### TCP BBR для ускорения скачивания ZIP

При установке/обновлении **из-под root** установщик автоматически пытается включить TCP BBR **на Linux-хосте**. Если модуль `tcp_bbr` доступен, `install.sh --deploy` применяет настройку и сохраняет собственные файлы в `/etc/sysctl.d/99-photosorter-bbr.conf` и `/etc/modules-load.d/99-photosorter-bbr.conf`. Рабочий `fq_codel` не изменяется. Установщик также задаёт такой же алгоритм в сетевом пространстве Docker-контейнера Caddy (через Compose `sysctls`), чтобы скачивание ZIP действительно использовало BBR. BBR действует на новые TCP-соединения **всего VPS**, не только PhotoSorter. Если сервер не поддерживает BBR или запуск не от root, выводится предупреждение, но установка Docker продолжается.

В `.env` можно добавить `PHOTOSORTER_ENABLE_BBR=0`, чтобы **пропускать автоматическую настройку при будущих обновлениях** (это не отменяет уже применённую настройку). Для полного отката запусти от root: `bash PhotoSorter/tools/maintenance/setup_tcp_bbr.sh --disable`. Команда удаляет только файлы, созданные PhotoSorter, и переключает новые соединения хоста на `cubic`. Чтобы Caddy тоже перешёл на CUBIC, сначала выставь в `.env` `PHOTOSORTER_ENABLE_BBR=0`, затем выполни обычное обновление `bash ./install.sh --deploy` (Compose пересоздаст только изменённые сервисы). `bash ./install.sh --check` ничего не меняет и показывает текущий алгоритм. Проверка после перезагрузки: `sysctl net.ipv4.tcp_congestion_control`; сторонние sysctl-файлы могут переопределять значение.

### Обновление ранее установленного PhotoSorter

`git pull` и новая папка `git clone` **не сбрасывают существующую базу**. Compose использует постоянное имя `outdoor-sorter` и Docker volumes. Перед обновлением проверить `git status`, `./install.sh --check` и согласованную копию PostgreSQL + `PhotoSorter/data` + `Models` + `.env.generated` (внешнее защищённое хранилище, тест восстановления). После проверки бэкапа обновление запускают:

```bash
git fetch origin main
git switch main
git pull --ff-only origin main
bash ./install.sh --deploy
```

Если ранее сервер был на detached commit, сперва проверить локальные изменения: `git switch main` может требовать разрешения конфликтов. Устаревший токен `PHOTOSORTER_APPROVE_UPGRADE` установщику больше не нужен.

**Полный бета-сброс** (включая удаление базы, фотографий, SAM и исторических результатов) — отдельная операция, не часть `git pull` или `install.sh`. Инструкция: [SINGLE_SITE_INSTALL](docs/SINGLE_SITE_INSTALL.md). Не использовать `docker compose down -v` как команду обновления.

## Новые настройки CPU и создание конструкций

**Производительность:** доступное число CPU определяется на сервере. В «Настройки → Производительность» есть два связанных ползунка: «Модель» и «Система». Они задают общий бюджет единственному worker MegaLoc для ФО **и** подготовки Образцов: обе задачи выполняются последовательно в общей очереди. Модель получает указанное число вычислительных потоков и ограничение CPU affinity для следующей задачи, остальное количество ядер остаётся вне её affinity. Система не ограничивается этими оставшимися CPU и использует свободные ядра при отсутствии нагрузки модели. В Docker thumbnail/cleanup больше не имеют фиксированных 0.35/0.25 CPU: задаются только низкие относительные CPU shares 128/64. ZIP не перенастраивается.

**Образцы:** кнопка «Создать конструкцию» открывает единое модальное окно с тремя режимами: обычная конструкция по строгому формату `SAM 0004 — Гагарина 64` (код города вводится вручную: любые 2–5 латинских букв, автоматически в верхнем регистре; затем номер и адрес); индивидуальная конструкция со свободным безопасным названием; импорт готовой папки по старым строгим правилам. Созданные конструкции видны даже без фотографий; пустая конструкция не влияет на MegaLoc до завершения подготовки первых Образцов в очереди.

**Статусы:** карточки ФО, Очереди и Результатов имеют цветную обводку по состоянию. Обычная ошибка — красная обводка, **«Удаляется» — вся карточка окрашивается красным** во всех трёх разделах; при ошибке фоновой очистки отображается «Ошибка удаления». Подготовка ZIP показывается как часть статуса «В обработке», без отдельного цвета.

## Работа

1. **Образцы:** загрузить библиотеку конструкций в строгом формате `SAM 0004 — Гагарина 64` или `TLT 3245 — Южное шоссе 10`. Перед передачей все файлы и имена проверяются. Существующие конструкции дополняются без удаления и перезаписи; отдельные фото можно добавить в выбранную конструкцию.
2. **ФО:** загрузить папку фотоотчёта. Новые партии до передачи регистрируют неизменяемый манифест: относительные пути, имена, размеры и UUID каждого ожидаемого изображения. При обрыве VPN передача сама повторяется с подтверждённого смещения; после закрытия страницы нужно снова выбрать исходную папку. В галерее видны незавершённые передачи и отсутствующие файлы из манифеста. Партия получает статус завершённой **только** после финализации и проверки сохранения каждого ожидаемого оригинала. Старые партии без манифеста продолжают работать по прежним правилам.
3. **Автообработка (этап 2):** в «Настройки» можно включить автозапуск новых партий (по умолчанию **выключен**) и выбрать порог; при выборе каждой папки параметры задаются отдельно и сохраняются на сервере. После полного манифеста `cleanup` ставит одно задание в существующую очередь без открытого браузера. Автозапуск можно отменить до enqueue; старые партии и результаты не обрабатываются автоматически.
4. **ФО — контроль обработки (этап 3):** прямо в списке и карточке партии видно реальное состояние MegaLoc (`Не обработано`/очередь с номером/обрабатывается с прогрессом/завершено/ошибка/остановлено). **Зелёный** только полностью успешный запуск; готовые миниатюры не означают готовность MegaLoc. Действия: «Обработать» и «Повторить обработку» (тот же порог), отменить ожидающий автозапуск, убрать ещё не начатое задание из очереди, остановить выполняющееся, перейти к результатам. В карточке истории доступны все прежние запуски, включая результаты предыдущего успешного запуска после новой ошибки. Остановка выполняется через существующий API, с подтверждением; оригиналы не удаляются.
5. **Обработка (этап 4):** отдельная панель наблюдения MegaLoc: модель и состояние её загрузки, heartbeat Worker, общие сохранённые настройки (редактируются во вкладке «Настройки»), активное задание и достоверный progress текущего этапа, FIFO очередь и история. **В этом разделе нет второй формы запуска.** Новый запуск и повторная обработка доступны в «ФО». Очередные и текущие задания останавливаются через существующий API с подтверждением. Лёгкий запрос активных заданий выполняется независимо от истории, без опроса всех запусков каждые несколько секунд.
6. **Результаты:** проверить назначенные SAM и неопределённые фотографии; скачать полный ZIP. Полный ZIP создаётся автоматически после MegaLoc, до появления статуса «Завершено». Срок хранения от минуты до месяцев выбирается в настройках, по умолчанию 2 месяца.
7. **Логи и настройки:** следить за состоянием фоновых служб, диска, логами обработки и галереями. Настройки автообработки и порога хранятся в PostgreSQL; изменение значений не меняет уже созданные партии и snapshots заданий.

## Где хранятся данные

| Путь / Docker volume | Назначение |
|---|---|
| `Models/models/` | Веса моделей; вне Git |
| `Models/cache/` | Кэш загрузчиков и библиотек; вне Git |
| `PhotoSorter/data/references/` | Постоянные образцы конструкций; папка по неизменному ключу города и номера |
| `PhotoSorter/data/uploads/` | Оригиналы партий ФО |
| `PhotoSorter/data/runs/`, `outputs/` | История обработок и результаты |
| `PhotoSorter/data/cache/` | Только служебные кэши, в том числе WebP и embeddings образцов |
| `outdoor-sorter_postgres_data` | PostgreSQL: пользователи, партии, задания, очереди |
| `outdoor-sorter_caddy_data`, `caddy_config` | Сертификаты HTTPS и состояние Caddy |

**Файлы в `Models/` и `PhotoSorter/data/` не являются частью репозитория.** Изменение ветки не очищает их.

## Единственный путь обработки

Загрузка образцов всегда открыта, в том числе при выполняющихся и ожидающих ФО.
Браузер регистрирует полный manifest, допередаёт недостающие части в
`PhotoSorter/data/reference_staging/` и после завершения ставит **одну**
подготовку в общую `work_queue`. Worker выполняет ФО и подготовку строго
по `seq`, по одной тяжёлой задаче. Только подготовленная и целиком
опубликованная версия доступна следующему ФО. Активное ФО закрепляет свою
версию на фактическом старте. Никаких переменных выбора старого режима.

Чистая beta-установка из `main`:
```bash
cd ~/Sorter && git pull --ff-only origin main && bash ./install.sh --deploy
```

Проект экспериментальный: папки с тестовыми ФО и образцами находятся у владельца
на ПК, VPS можно полностью переустановить. Старые **базы предыдущих бета-версий**
не мигрируем автоматически в новую архитектуру — при смене схемы используем
чистую установку. Установка сама ничего не удаляет.
Технические подробности: [REFERENCE_PIPELINE](docs/REFERENCE_PIPELINE.md).


## Компактный интерфейс и скачивание ZIP (beta)

Разделы: **Фотографии**, **Образцы**, **Очередь**, **Результаты**,
**Логи**, **Настройки**. Отдельной вкладки «Обработка» больше нет:
её подробности находятся в `/queue/runs/:runId`, управление MegaLoc и
параметры CPU — в «Настройках».

Общее окно загрузки монтируется в `Shell` и не прерывает передачу при
сворачивании или переходах между вкладками. Отдельная пара прокруток в
«Образцах» работает на десктопе; мобильный интерфейс прокручивается обычным
образом. Цветовые акценты карточек соответствуют общей монохромной теме.

ZIP теперь создаётся **один раз** в `data/outputs/<run-id>/.archives`,
после чего обслуживается `FileResponse` с поддержкой скачивания с позиции
после обрыва; очистка результата удаляет и кэш архивов. Полный ZIP создаётся в завершающем этапе обработки, а не по клику скачивания. Сервер не хранит
постоянные альтернативные версии обработчиков.

## Автоархив, срок хранения, CPU

Новые успешные MegaLoc задачи завершаются лишь после готовности полного ZIP. Архив хранится внутри `data/outputs/<run-id>/.archives/` и автоматически удаляется при удалении партии. Если архив создать не удалось, его можно подготовить повторно из готовых результатов без повторной сортировки. В интерфейсе ZIP отображается как маленький процент под общей полосой обработки.

В настройках хранилища задаётся автоудаление через минуты/часы/дни/месяцы, либо выключается. По умолчанию два месяца после успешного архива. Новые значения не сокращают сроки существующих партий. CPU MegaLoc для ФО/образцов настраивается отдельно; лимиты Docker служб остаются инфраструктурными.

## Эксперимент: разметка экранов (этап 1)

Тестовая ветка `feature/ad-recognition` сохраняет MegaLoc, единую FIFO-очередь, ZIP и текущий Vue SPA. Во вкладке **Образцы** откройте фотографию и нажмите **Выделить экран**. Перемещайте четыре угла, выбирайте толщину полосы поиска, название экрана и сохраняйте. Для следующего ракурса можно выбрать уже существующий экран. Несколько экранов одной конструкции имеют разные ID; разметки разных конструкций не смешиваются.

Координаты и толщина — в пикселях исходного изображения после EXIF-ориентации. Разметка и номер версии хранятся в PostgreSQL. Это **не** подключает XFeat, DINOv2, OCR или оценку качества к задачам ФО: на этапе 1 действующая обработка остаётся MegaLoc-only.

Инструкция для чистого нового VPS: `git clone --single-branch --branch feature/ad-recognition https://github.com/chapaayy/Sorter.git`, затем `cd Sorter && cp .env.example .env`, настройте `.env` и выполните `bash ./install.sh --check` и `bash ./install.sh --deploy`. При первом `--check` отсутствие `.env.generated` ожидаемо; секреты создаёт первоначальный `--deploy`. Не выполнять сброс базы или volumes при обычном обновлении.
