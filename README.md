# MAP

**Match, Assign, Package.** Название в интерфейсе. Репозиторий Sorter, каталоги PhotoSorter и конфигурация установки остаются прежними.

**Бета · один сайт · основная ветка `main`.** Приватная система сортировки фотоотчётов наружной рекламы по конструкциям. Сейчас используется одна модель MegaLoc: она сначала группирует фотографии ФО (порог по умолчанию **0.50**), затем сопоставляет группы с общей библиотекой образцов SAM. Нейросетевая математика не меняется при переработке интерфейса.

## Одна актуальная версия

- Сайт: `https://<DOMAIN>/` — **Vue 3 + TypeScript**, без `/v3/` и параллельного старого интерфейса.
- Страницы: `/fo`, `/references`, `/queue`, `/results`, `/logs`, `/settings`. Подробности запуска: `/queue/runs/:runId`. Вход: `/login`, заявка на доступ: `/register`.
- Загрузки можно свернуть и перейти в другой раздел MAP. Индикатор возвращает к передаче. После завершения сайт показывает уведомление без автоматического перехода. Если закрыть или обновить вкладку браузера, для докачки нужно снова выбрать исходные файлы.
- API: `/api/*` на том же домене. Данные и авторизация остаются на сервере.
- Код развивается в **`main`**; отдельные исторические ветки не являются версиями для установки.
- `PhotoSorter/frontend/static/` удалён. Единственный frontend — `PhotoSorter/frontend/src/`; результат сборки находится в игнорируемом `dist/`.

## Установка на новый пустой сервер

Linux x86-64, собственный домен с DNS на сервер и доступные TCP 80/443. На чистой Ubuntu или Debian запускай установщик от root. Он сам поставит Docker Engine, Compose v2 и Python 3, если их нет. На других дистрибутивах установи эти зависимости заранее. Целевая конфигурация: 8 vCPU, около 24 ГБ RAM и 200 ГБ диска.

```bash
git clone --branch main --single-branch https://github.com/chapaayy/Sorter.git /opt/Sorter
cd /opt/Sorter
cp .env.example .env
nano .env            # DOMAIN и свой ADMIN_PASSWORD
bash ./install.sh --deploy
```

Если на сервере нет Git или редактора, выполни перед клонированием `apt-get update && apt-get install -y git nano`.

Логин — `admin`. Пароль задай сам в `.env`, например в формате `ADMIN_PASSWORD='…'` (16–256 символов, одинарные кавычки). Это действующий пароль, а не временный. Чтобы его сменить, обнови `.env` и запусти `bash ./install.sh --deploy`. Сессия действует 7 дней и переживает перезапуск API с тем же паролем. При смене пароля или первом обновлении с миграцией `0028_owner_session_rotation.sql` прежние сессии админа закрываются. `.env.generated` содержит только автоматически созданный служебный пароль PostgreSQL. Оба файла приватные и не добавляются в Git. Модель/веса можно загрузить из веб-интерфейса.

В результате поднимаются `caddy` (HTTPS), `postgres`, `api`, `worker` (MegaLoc), `thumbnail` (WebP) и `cleanup` (служебная очистка). Снаружи публикуются только 80/443.

### TCP BBR для ускорения скачивания ZIP

При установке/обновлении **из-под root** установщик автоматически пытается включить TCP BBR **на Linux-хосте**. Если модуль `tcp_bbr` доступен, `install.sh --deploy` применяет настройку и сохраняет собственные файлы в `/etc/sysctl.d/99-photosorter-bbr.conf` и `/etc/modules-load.d/99-photosorter-bbr.conf`. Рабочий `fq_codel` не изменяется. Установщик также задаёт такой же алгоритм в сетевом пространстве Docker-контейнера Caddy (через Compose `sysctls`), чтобы скачивание ZIP действительно использовало BBR. BBR действует на новые TCP-соединения **всего VPS**, не только PhotoSorter. Если сервер не поддерживает BBR или запуск не от root, выводится предупреждение, но установка Docker продолжается.

В `.env` можно добавить `PHOTOSORTER_ENABLE_BBR=0`, чтобы **пропускать автоматическую настройку при будущих обновлениях** (это не отменяет уже применённую настройку). Для полного отката запусти от root: `bash PhotoSorter/tools/maintenance/setup_tcp_bbr.sh --disable`. Команда удаляет только файлы, созданные PhotoSorter, и переключает новые соединения хоста на `cubic`. Чтобы Caddy тоже перешёл на CUBIC, сначала выставь в `.env` `PHOTOSORTER_ENABLE_BBR=0`, затем выполни обычное обновление `bash ./install.sh --deploy` (Compose пересоздаст только изменённые сервисы). `bash ./install.sh --check` ничего не меняет и показывает текущий алгоритм. Проверка после перезагрузки: `sysctl net.ipv4.tcp_congestion_control`; сторонние sysctl-файлы могут переопределять значение.

### Обновление ранее установленного PhotoSorter

`git pull` и новая папка `git clone` **не сбрасывают существующую базу**. Compose использует постоянное имя `outdoor-sorter` и Docker volumes. Перед обновлением проверить `git status`, `./install.sh --check` и согласованную копию PostgreSQL + `PhotoSorter/data` + `Models` + `.env` + `.env.generated` (внешнее защищённое хранилище, тест восстановления). Если прежняя установка генерировала пароль админа, перед запуском нового установщика задай `ADMIN_PASSWORD` в `.env`. После проверки бэкапа обновление запускают:

```bash
git fetch origin main
git switch main
git pull --ff-only origin main
bash ./install.sh --deploy
```

Если ранее сервер был на detached commit, сперва проверить локальные изменения: `git switch main` может требовать разрешения конфликтов. Устаревший токен `PHOTOSORTER_APPROVE_UPGRADE` установщику больше не нужен.

**Полный бета-сброс** (включая удаление базы, фотографий, SAM и исторических результатов) — отдельная операция, не часть `git pull` или `install.sh`. Инструкция: [SINGLE_SITE_INSTALL](docs/SINGLE_SITE_INSTALL.md). Не использовать `docker compose down -v` как команду обновления.

## Доступ к готовым фотоотчётам

Под `admin` открой «Администрирование → Аккаунты → Создать пользователя». Укажи почту и начальный пароль от 12 символов, затем выбери готовые результаты. Аккаунт сразу активен даже без выбранных отчётов. Доступ можно изменить или снять из списка аккаунтов. Письма не отправляются автоматически.

Ссылка «Зарегистрироваться» на странице входа по-прежнему открывает заявку. В «Администрировании» владелец читает комментарий, отклоняет заявку или одобряет её и выдаёт доступ. Пользователь входит по почте и паролю, видит только выбранные готовые результаты и может скачать их ZIP. На новые отчёты доступ автоматически не распространяется. `ADMIN_PASSWORD` по-прежнему берётся из `.env`.

## Новые настройки CPU и создание конструкций

**Производительность:** доступное число CPU определяется на сервере. В «Настройки → Производительность» есть два связанных ползунка: «Модель» и «Система». Они задают общий бюджет единственному worker MegaLoc для ФО **и** подготовки Образцов: обе задачи выполняются последовательно в общей очереди. Модель получает указанное число вычислительных потоков и ограничение CPU affinity для следующей задачи, остальное количество ядер остаётся вне её affinity. Система не ограничивается этими оставшимися CPU и использует свободные ядра при отсутствии нагрузки модели. В Docker thumbnail/cleanup больше не имеют фиксированных 0.35/0.25 CPU: задаются только низкие относительные CPU shares 128/64. ZIP не перенастраивается.

**Образцы:** кнопка «Создать конструкцию» открывает единое модальное окно с тремя режимами: обычная конструкция по строгому формату `SAM 0004 — Гагарина 64` (код города вводится вручную: любые 2–5 латинских букв, автоматически в верхнем регистре; затем номер и адрес); индивидуальная конструкция со свободным безопасным названием; импорт готовой папки по старым строгим правилам. Созданные конструкции видны даже без фотографий; пустая конструкция не влияет на MegaLoc до завершения подготовки первых Образцов в очереди.

**Статусы:** карточки ФО, Очереди и Результатов имеют цветную обводку по состоянию. Обычная ошибка — красная обводка, **«Удаляется» — вся карточка окрашивается красным** во всех трёх разделах; при ошибке фоновой очистки отображается «Ошибка удаления». ZIP создаётся при скачивании, не является стадией обработки.

## Работа

1. **Образцы:** загрузить библиотеку конструкций в строгом формате `SAM 0004 — Гагарина 64` или `TLT 3245 — Южное шоссе 10`. Перед передачей MAP показывает списки новых фото и точных дублей. После подтверждения передаются только новые файлы. Если остались одни дубли, подготовка не ставится в очередь. Отдельные фото можно добавить в выбранную конструкцию.
2. **ФО:** одна папка с фото и видео до 2 ГиБ на файл. Выберите целевой формат фото (по умолчанию JPG, также PNG) и видео (по умолчанию MP4 H.264/AAC, также WebM VP9/Opus). Оригиналы сохраняются, совместимые файлы не пережимаются. JPG/JPEG с дополнительными JPEG-кадрами (MPO) при выборе JPG сохраняются целиком, а для сортировки берётся основное изображение. Если нужна подготовка, после загрузки всей папки появляется задача «Перекодирование файлов» в общей FIFO перед сортировкой этой партии. Контейнер и несовместимые дорожки меняются только там, где необходимо. В существующей плашке очереди отображаются текущий файл, общий прогресс и оценка времени до конца перекодирования партии, когда накопилось достаточно данных. FFmpeg использует потоки в пределах CPU-бюджета воркера. Превью фото и обложки видео готовятся в фоновом воркере миниатюр. Галерея открывает файлы во встроенном просмотрщике даже при перекодировании: если исходный формат не поддерживается браузером, пока доступно превью или обложка, когда они готовы. Удаление партии ждёт активную передачу, но не завершившийся с ошибкой или оборванный просмотр. Пока браузер передаёт папку, в карточке видны подтверждённые байты партии и текущих файлов. Блок восстановления появляется только для незавершённой передачи, которой нет в очереди этой вкладки. В Образцы по-прежнему загружаются только поддерживаемые фотографии.
   Перед импортом можно изменить название фотоотчёта. Имя папки подставляется по умолчанию. Каждый новый импорт создаёт отдельную партию, а при совпадении имени сервер добавляет « 2», « 3» и так далее. Новые партии до передачи регистрируют неизменяемый манифест: относительные пути, имена, размеры и UUID всех ожидаемых файлов. При обрыве VPN передача повторяется с подтверждённого смещения. После закрытия страницы откройте незавершённый ФО, нажмите «Продолжить загрузку папки» и выберите исходную папку. Партия получает статус завершённой только после проверки сохранения каждого оригинала. Для старых партий без манифеста сохраняется восстановление отдельных файлов.
3. **Автообработка (этап 2):** в «Настройки» можно включить автозапуск новых партий (по умолчанию **выключен**) и выбрать порог; при выборе каждой папки параметры задаются отдельно и сохраняются на сервере. После полного манифеста `cleanup` ставит одно задание в существующую очередь без открытого браузера. Автозапуск можно отменить до enqueue; старые партии и результаты не обрабатываются автоматически.
4. **ФО — контроль обработки (этап 3):** прямо в списке и карточке партии видно реальное состояние MegaLoc (`Не обработано`/очередь с номером/обрабатывается с прогрессом/завершено/ошибка/остановлено). **Зелёный** только полностью успешный запуск; готовые миниатюры не означают готовность MegaLoc. Действия: «Обработать» и «Повторить обработку» (тот же порог), отменить ожидающий автозапуск, убрать ещё не начатое задание из очереди, остановить выполняющееся, перейти к результатам. В карточке истории доступны все прежние запуски, включая результаты предыдущего успешного запуска после новой ошибки. Остановка выполняется через существующий API, с подтверждением; оригиналы не удаляются.
5. **Обработка (этап 4):** отдельная панель наблюдения MegaLoc: модель и состояние её загрузки, heartbeat Worker, общие сохранённые настройки (редактируются во вкладке «Настройки»), активное задание и достоверный progress текущего этапа, FIFO очередь и история. **В этом разделе нет второй формы запуска.** Новый запуск и повторная обработка доступны в «ФО». Очередные и текущие задания останавливаются через существующий API с подтверждением. Лёгкий запрос активных заданий выполняется независимо от истории, без опроса всех запусков каждые несколько секунд.
6. **Результаты:** проверить назначенные SAM и неопределённые фотографии; скачать полный ZIP. Полный ZIP создаётся по запросу после сохранения результата MegaLoc. Срок хранения от минуты до месяцев выбирается в настройках, по умолчанию 2 месяца. Видео сопоставляется с конструкцией по максимум восьми временным срезам (первый, последний и шесть между ними), не участвует в группировке фото и появляется одним целым клипом в результатах и ZIP. Если признаки разных кадров противоречат друг другу, ролик попадает в `_Неопределено`. Файлы, которые не удалось привести к выбранному формату, остаются в партии с ошибкой и не включаются в ZIP.
7. **Логи и настройки:** следить за состоянием фоновых служб, диска, логами обработки и галереями. Настройки автообработки и порога хранятся в PostgreSQL; изменение значений не меняет уже созданные партии и snapshots заданий.

## Где хранятся данные

| Путь / Docker volume | Назначение |
|---|---|
| `Models/models/` | Веса моделей; вне Git |
| `Models/cache/` | Кэш загрузчиков и библиотек; вне Git |
| `PhotoSorter/data/references/` | Постоянные образцы конструкций; папка по неизменному ключу города и номера |
| `PhotoSorter/data/uploads/` | Оригиналы партий ФО и подготовленные копии в `.normalized/` |
| `PhotoSorter/data/runs/`, `outputs/` | История обработок и результаты |
| `PhotoSorter/data/cache/` | Только служебные кэши, в том числе WebP и embeddings образцов |
| `outdoor-sorter_postgres_data` | PostgreSQL: пользователи, партии, задания, очереди |
| `outdoor-sorter_caddy_data`, `caddy_config` | Сертификаты HTTPS и состояние Caddy |

**Файлы в `Models/` и `PhotoSorter/data/` не являются частью репозитория.** Изменение ветки не очищает их.

## Единственный путь обработки

Загрузка образцов всегда открыта, в том числе при выполняющихся и ожидающих ФО.
Браузер регистрирует manifest подтверждённых новых образцов и допередаёт недостающие части в
`PhotoSorter/data/reference_staging/`. После завершения сервер ставит **одну**
подготовку в общую `work_queue`, только если есть новые сохранённые образцы.
Worker выполняет ФО и подготовку строго
по `seq`, по одной тяжёлой задаче. Только подготовленная и целиком
опубликованная версия доступна следующему ФО. Активное ФО закрепляет свою
версию на фактическом старте. Никаких переменных выбора старого режима.
Worker заранее загружает установленную MegaLoc в RAM и сохраняет один
экземпляр между задачами, пока не изменится версия модели или не завершится
процесс. Число CPU-потоков применяется перед очередной задачей. Активный
прогресс в интерфейсе обновляется примерно раз в секунду.

Чистая beta-установка из `main`:
```bash
cd ~/Sorter && git pull --ff-only origin main && bash ./install.sh --deploy
```

Проект экспериментальный: папки с тестовыми ФО и образцами находятся у владельца
на ПК, VPS можно полностью переустановить. Старые **базы предыдущих бета-версий**
не мигрируем автоматически в новую архитектуру — при смене схемы используем
чистую установку. Установка сама ничего не удаляет.
Технические подробности: [REFERENCE_PIPELINE](docs/REFERENCE_PIPELINE.md).


## Компактный интерфейс и скачивание ZIP (beta)

Разделы: **Фотографии**, **Образцы**, **Очередь**, **Результаты**,
**Логи**, **Настройки**. Отдельной вкладки «Обработка» больше нет:
её подробности находятся в `/queue/runs/:runId`, управление MegaLoc и
параметры CPU — в «Настройках».

Все настройки собраны в одной прокручиваемой колонке. В «Оформлении»
три карточки показывают превью тем MAP. При первой загрузке списков и
галерей скелетоны сохраняют место под контент, а медленные изображения
не задерживают появление текста и действий.

ФО и образцы используют отдельную браузерную очередь передачи **на сайт**.
Форму выбора папки можно открывать снова во время активной загрузки
и добавлять следующие папки. В правом нижнем углу видна только текущая
передача. Её статус и процент также видны в карточке соответствующего ФО.
Клик по плашке или «Ход загрузки» открывает весь список, где можно приостановить, продолжить
или отменить текущую и убрать ожидающую. Следующая начинается после
завершения или отмены текущей, независимо от очереди MegaLoc.
Переходы по разделам MAP не прерывают загрузку. После перезагрузки вкладки
для докачки откройте незавершённый ФО и снова выберите исходную папку.

На десктопе в «Образцах» две независимые области прокрутки, на телефоне
интерфейс прокручивается обычным образом.

Готовый ZIP переиспользуется из `data/outputs/<run-id>/.archives`,
после чего обслуживается `FileResponse` с поддержкой скачивания с позиции
после обрыва; очистка результата удаляет и кэш архивов. Полный ZIP создаётся только по клику скачивания, кэшируется на 3600 секунд. Сервер не хранит
постоянные альтернативные версии обработчиков.
ZIP и его верхняя папка называются как фотоотчёт. Папки конструкций
получают названия из «Образцов», а снимки сохраняют оригинальные имена.
Если в одной папке два одинаковых имени, добавляется « (2)», « (3)» и т. д.
Недопустимые для Windows символы заменяются. Для ранее готового результата
новый формат собирается при первом повторном скачивании без запуска MegaLoc.

## ZIP по запросу, срок хранения, CPU

Успешные задачи MegaLoc завершаются после сохранения результатов и манифеста. ZIP хранится временно в `data/outputs/<run-id>/.archives/`; cleanup проверяет TTL 3600 секунд примерно каждые 30 секунд, не удаляя активные скачивания. Ошибка скачивания не меняет статус результата; следующий запрос может пересобрать ZIP без сортировки.

В настройках хранилища задаётся автоудаление через минуты/часы/дни/месяцы, либо выключается. По умолчанию два месяца после завершения результата. Новые значения не сокращают сроки существующих партий. В карточке виден этап удаления, а во время длительной операции — её прогресс. Если партия удалится между обновлениями, MAP сразу сообщит о завершении. CPU MegaLoc для ФО/образцов настраивается отдельно; лимиты Docker служб остаются инфраструктурными.


**Отсев ошибочных совпадений MegaLoc:** в «Настройки → MegaLoc» отдельно от порога группировки доступно «Минимальное сходство с образцами» (0.000–1.000). Например, при 0.200 кадр с 0.097 попадёт в «Неопределено», а с 0.234 — останется. Проверяется отдельная фотография, в том числе внутри группы ФО. Значение 0.000 отключает фильтр. Изменения действуют только на новые запуски (ручные и автоматические), старые готовые ZIP не меняются.
