# Outdoor PhotoSorter — единая архитектура образцов и FIFO

**Текущая beta-система**. Удалены старый планировщик, загрузка образцов через
`/api/uploads`, переключатели реализации и сканирование живых эталонов из
MegaLoc-Worker. Структура строго модульная, одна ответственность на файл.

## Работа

1. Вкладка «Образцы» всегда разрешает новую загрузку, включая обработку ФО.
   Полный манифест (SAM, адрес, относительный путь, UUID, размер и SHA-256)
   регистрируется **до** передачи первого блока.
2. Файлы передаются по частям не более 16 МиБ непосредственно на сервер
   `PhotoSorter/data/reference_staging/<session-uuid>/`. В БД хранятся
   смещения и подтверждения. После потери связи исходные файлы можно выбрать
   повторно: совпавший манифест досылает только недостающие байты.
3. Сервер проверяет SHA-256, формат, размеры и реальное наличие дублей.
   После подтверждения **всех** файлов одной сессии атомарно создаёт
   `reference_preparation_jobs` и запись в **единой** `work_queue`.
   Две разные завершённые сессии дают две подготовки, даже если содержат
   лишь дубли. Половинчатая сессия не создаёт prep job.
4. Единственный `server/worker.py` владеет глобальным advisory leader lock,
   читает задачи в порядке `work_queue.seq`. Одновременно выполняется
   одна CPU-задача MegaLoc — либо подготовка эталонов, либо обработка ФО.
5. Подготовка использует общий reference cache по SHA-256 исходника и
   сигнатуре установленной MegaLoc. Только полностью проверенный новый
   состав публикуется **одной транзакцией** через
   `reference_library_state.current_version_id`.
6. ФО при фактическом claim получает `reference_version_id`,
   `manifest_digest`, `model_signature` и **точный immutable список**
   образцов. Никакого поиска новых файлов в `data/references/` во время
   обработки; уже работающие ФО не меняют версию при публикации.
7. Если подготовка завершилась ошибкой или прервалась, FIFO блокирует
   все следующие задачи. Администратор явно нажимает retry/skip в /queue.
   Пропуск не публикует новые образцы.
8. `reference_library_events` и `library_notice_cursors` формируют
   одно уведомление об опубликованном изменении библиотеки после предыдущей
   ФО. Показ истории не является подтверждением; только «Понятно» выполняет
   idempotent ack в PostgreSQL.

## Первая установка

Чистая БД автоматически получает **пустую библиотеку V1**. Загрузка первых
эталонов сразу доступна, после подготовки публикуется V2. Если ФО пытается
стартовать до первой подготовки, сервер корректно сообщает об отсутствии
готовых образцов. Источник исходных тестовых фото/образцов — ПК владельца.
Старые данные на beta-VPS не требуют специальной совместимости; старую БД
нужно сбрасывать **явно**, если она создана иной архитектурой.

## Структура и границы модулей

- `server/db/repositories/work_queue.py`: один FIFO dispatcher и recovery.
- `server/worker.py`: только роль лидера и выбор типа CPU-задачи.
- `server/jobs.py` и `app/jobs/worker.py`: запуск, обработка и результат ФО.
- `server/uploads.py`: только приём файлов ФО, манифест/автопостановка.
- `server/services/reference_imports.py`: регистрация и завершение сессии.
- `server/services/reference_uploads.py`: чанки, проверка, дедупликация.
- `server/storage/reference_objects.py`: файловое staging-хранилище.
- `server/workers/reference_prepare.py`: подготовка признаков и шаг публикации.
- `server/services/reference_publication.py`: immutable версии и V1.
- `server/services/reference_gallery.py`: индекс/миниатюры для UI, не источник inference.
- `server/services/references.py`: удаление через новую опубликованную версию,
   без удаления объектов прежних снимков.
- `server/services/construction_catalog.py`: метаданные адресов, не inference.
- `frontend/src/composables/useReferenceTransfer.ts`: единственный клиент загрузки образцов.
- `frontend/src/features/queue/`: общая FIFO (не отдельная старая очередь).
- `frontend/src/features/references/`: текущие образцы + загрузка/подготовка.

## Проверки

До приёмки: fresh DB → первый импорт, 5 ФО → подготовка → ФО,
параллельная загрузка образцов при выполняющейся ФО,
дубли и отсутствие изменений версии при duplicate-only,
обрыв сети и refresh, повреждённое изображение, рестарт worker,
ошибка/skip/retry, неверные SAM и адрес, количество миниатюр и работа
удаления, актуальные уведомления в Chromium/WebKit.

Алгоритмы группировки/сопоставления MegaLoc не трогать. Настройки
числа потоков и размера CPU batch — эксплуатационные, **не переключатели
старого и нового функционала**.


## Отображение и работа с результатами

Образцы загружаются через общий глобальный диалог Shell,
публикация показывается только при актуальной работе и ошибках в
«Очереди». Успешный снимок не занимает отдельную панель на странице
образцов. ФО и подготовка используют один FIFO. ZIP результатов формируется
один раз и затем отдаётся с HTTP byte ranges, без второго Worker.

## Разметка экрана — независимый этап UI (feature/ad-recognition)

Разметка привязывается только к опубликованным фотографиям Образцов,
не к staging-файлам. Физический экран имеет устойчивый UUID в
`reference_screens`, а каждый его ракурс — самостоятельную запись с
UUID Образца, SHA, четырьмя углами, толщиной полосы и номером версии.
При удалении опубликованного фото запись разметки удаляется по FK.
Существующие функции подготовки MegaLoc, публикации библиотеки и FIFO
не изменены. XFeat и автоматический поиск экранов ещё не подключены.
