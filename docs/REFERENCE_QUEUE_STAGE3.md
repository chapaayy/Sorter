# PhotoSorter — этап 3: общий CPU Worker, FIFO и version-pinned образцы

Реализация по согласованному плану от 07.11.2026. Код добавлен в `main`, но **промышленная активация на VPS не производится автоматически**.

## Граница включения

- `PHOTOSORTER_UNIFIED_QUEUE=1`: новый планировщик `work_queue`, общий leader advisory lock (прежний ключ), отдельная подготовка и snapshot образцов для ФО. Без переключателя сохраняется старый планировщик, что позволяет принять миграции без переключения обработки.
- `REFERENCE_IMPORT_STAGING_ENABLED=1` **и** `PHOTOSORTER_UNIFIED_QUEUE=1`: API staging-сессий образцов. Нельзя включать staging отдельно от общего Worker.
- До согласованного обновления на VPS/проверенного offsite backup оба переключателя остаются выключены. Вкладка «Образцы» пока использует legacy UI. Снятие старой блокировки загрузки — этап 4, после интеграционной приёмки.

## FIFO и снимок ФО

Каждый новый /api/runs enqueue помещает ФО в `jobs` и `work_queue` в одной транзакции под advisory lock `723409133`. Старые queued jobs подхватываются через idempotent backfill. Одна последовательность `seq` для ФО и подготовок образцов. При включённом новом worker ФО получает `reference_version`, `model_signature`, `reference_manifest_digest` и точный `reference_members` **при фактическом claim**, а не при регистрации. Из `app/jobs/worker.py` меняется только источник списка образцов: группировка MegaLoc (`app/recognition/`) не тронута. Признаки кэшируются по SHA-256 + сигнатуре модели, ФО не кэшируются.

Для legacy образцов первая активация создаёт защищённые копии в `data/reference_objects/legacy/` и новую опубликованную версию; оригинальные файлы и IDs не меняются. Перед claim синхронизируется состав старых загруженных образцов (без включения ещё не подготовленного staging). При несовпадении модели или отсутствии файла claim отказывает, не маскируя ошибку.

## Подготовка образцов

Отдельный `reference_preparation_jobs` запускается тем же главным Worker; одновременно два тяжёлых задания не выполняются. Сначала проверяются immutable файлы staging и кэш, затем только недостающие признаки; MegaLoc загружается лишь если кэша не хватает. После полной проверки новые члены версии публикуются одним PostgreSQL коммитом вместе с обновлением `reference_library_state` и статусами job. Галерея получает legacy-совместимые hardlinks, но новая сортировка использует immutable исходники.

При ошибке задача становится `failed`, а следующее ФО по FIFO не стартует; администратор может явно `POST /api/reference-preparations/{id}/retry` либо `/skip` с телом `{"idempotency_key":"UUID"}`. Пропуск означает **сохранение старой опубликованной версии**, не успех подготовки. Crash/restart отмечает interrupted, без автоматического обхода зависимости. Текущие результаты ФО не пересортировываются.

## API

- `GET /api/work-queue?limit=100&offset=0`: общая очередь, позиции, типы и статусы.
- `GET /api/reference-preparations/{id}`: время, прогресс, ошибки.
- `POST /api/reference-preparations/{id}/retry`, `/skip`: явное восстановление зависимостей, идемпотентное по ключу.
- `/api/runs`, `/api/batches`, `/api/results` сохраняют старые контракты.
- Завершение нового ФО-манифеста при объединённом режиме резервирует позицию через автоenqueue в той же SQL-транзакции, не дожидаясь очередного тикa cleanup.

## Безопасность и долги перед staging acceptance

Это **не** запуск на боевой базе и не доказательство идентичности группировки реальных 189/1315 ФО. Перед включением: проверить внешнюю копию БД/PostgreSQL + файлы данных + модели, восстановление на отдельном сервере, миграции 0011–0015, отсутствие symlinks/orphans, сценарий 5 ФО → 1 подготовка → 1 ФО, ошибки + retry/skip + restart, RAM/CPU/throughput. Не применять `docker compose down -v`; не включать переключатели без проверки соответствующей настройки у API и Worker. UI, уведомления и полноценная UX-обработка ошибок — этап 4.
