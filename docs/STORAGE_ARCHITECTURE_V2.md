# MAP storage architecture v2 — target contract (stage 1)
Baseline: [c6d77ebb1c9c80c732df209a17a993dd38ec381f](https://github.com/chapaayy/Sorter/commit/c6d77ebb1c9c80c732df209a17a993dd38ec381f). Branch: `feature/storage-architecture-v2`. **Not active yet**; do not deploy this stage as v2. Fresh installation only; no old-data migration.
The machine-readable source of category policy is [storage-layout-v2.json](storage-layout-v2.json). Existing production paths remain unchanged until subsequent stages.
## Boundaries
- Root-owned project and storage root, default /opt/Sorter/storage. Only authorized subdirectories writable. One app bind mount at /storage/app for API, worker, cleanup and thumbnail (10001:10001), not separately mounted media paths. Logs separate per service; processing log read access must be scoped. PGDATA and Caddy TLS/config private, no application mount. Updater backup/workspace/private root-only; durable control read-only to app; narrow Unix RPC API only. Exact PostgreSQL/Caddy UID/GID and native log permissions require image verification in stage 6. Engine and system runtime remain outside storage.
- App subtree: users, shared/references, temporary, models/megaloc, cache, state. Infrastructure subtree: postgres/data and caddy/data, caddy/config. Logs subtree: api, worker, cleanup, thumbnail, processing, postgres, caddy/access, caddy/runtime, models, updater, audit. System subtree: backups/updater, updater/control, updater/private, updater/workspace, audits, state. Git and build context exclude entire storage and credentials (stage 2).
- Typed relative keys, numeric user ID (users.id BIGINT), UUID for batch/upload/session, current run ID format YYYYMMDDTHHMMSS-12hex; stable construction ID to be resolved in stage 4; full SHA256 and validated model signature. Filename/display names are metadata, never physical path authority. No symlink traversal, no client absolute paths; ownership checks separate from path validation. Same mount real link/rename tests required.
- Reuse existing server/storage, app/config as facade to neutral pure config/path types. Do not add a second active registry or root. DB state and operation leases govern publication/cleanup; no unconditional recursive delete. Staged -> verified -> atomic publish -> DB commit, reconcile interrupted boundary with idempotent operation keys.
## Ownership and dependency policy
Current users access_role owner/viewer, result_access_grants(user_id,run_id) are permission only. Stage 2 add batches.owner_id FK to users.id, non-cascading delete, index, explicit authenticated creator. Jobs/uploads inherit through batch_id. Viewer cannot create/delete by receiving grant. Shared references and retained historical memberships/pinned jobs are not personal charge. Preserve historical versions until dependency and recovery semantics are proved; no age-based embedding or thumbnail purge. Source/hash/signature validation and GC locking must be verified in stage 4.
## Accounting
Logical st_size, allocated st_blocks*512, reserved bytes independent; physical unique (st_dev,st_ino) per snapshot, not durable identity. Proposed quota charge max(logical,allocated) once per persistent owner object; copies charge, hardlinks do not double charge. Directory metadata and deleted-open handles separately reconciled with per-filesystem statvfs; tmpfs memory separate. No new quotas enabled, no new personal eviction. Unknown visible, never auto-deleted.

## Stage 4 reference ownership and history policy
- The shared CAS is keyed by the full SHA-256 of original content, independent of SAM, region, address and filename. Import parts are session/upload UUID keys. Publication validates size, image and digest, uses a same-mount hardlink, verifies existing objects before reuse, then commits the receipt before unlinking the part. Gallery is a PostgreSQL projection, not a second media tree. Identical bytes can belong to different constructions; their logical IDs and sides remain distinct.
- Current-version pointer and retained version members are the authoritative library. The global FIFO gate pins a version at claim (earlier preparations take effect before later queued FO). Each claimed job has an explicit FK and immutable member snapshot. All retained jobs protect their version, including terminal jobs; inconsistent pins block collection. Historical header/events remain indefinitely. There is no user-facing restoration of arbitrary old library versions. Superseded versions with no job pin and no current pointer may retire their member sets after 30 days from supersession. Retired headers cannot be re-opened as complete versions. This is not a TTL for active/pinned samples.
- Physical SHA objects and all their model-signature embeddings are protected by retained members, current gallery records, and pending/retryable imports. After the last dependency disappears, collect marks a candidate; after 24h, rechecks graph under FIFO and exclusive reader lock and unlinks only verified canonical files. Unknown paths and mismatched metadata fail closed. A shared reader lock covers preview rendering/streaming and reference ZIP source reads. Stale incomplete reference imports may be cancelled after 30 days without transfer activity, only when their transfer locks can be acquired. Finalized transfer receipts do not permanently own bytes.
- Embeddings are keyed by the exact model/source/preprocessing content signature and SHA-256, store NPY checksum and dimensions, and validate shape, dtype, finite values and content on read. Ordinary deployment/touch/rename of unchanged assets does not invalidate the cache. No LRU, byte-size eviction, TTL or blanket old-signature purge. Actual offline inference with real MegaLoc remains a stage 5 acceptance criterion.
- Personal thumbnails are scoped by owner ID, shared reference thumbnails by content, both versioned WebP with atomic publication. Same-owner reuse only. Dependency-based candidates wait 24h, then recheck. History-only object/cache disk bytes are reported separately as a subset of shared space. Quotas and full accounting reconciliation remain later stages. ZIP location and model working source/weights layout are intentionally unchanged until stage 5.


## Stage 5 temporary pool and offline model policy
- On-demand results and per-construction ZIPs share `app/temporary/archives/results/<run_id>/`; reference exports use `app/temporary/archives/references/<plan_sha256>.zip`. Identity includes the immutable export plan; same-key flock serializes construction and directory shared pins protect HTTP readers through response close. CRC/count verification precedes publication. The 3600-second lifetime starts at publication, never at the last read. Expired ZIPs are rebuilt only on a new request; periodic nonblocking sweep every 30 seconds removes recognized expired files and unused locks. Active readers/builders defer deletion. Same-filesystem allocation admission serializes heavyweight ZIP/model allocations and retains the configured free-space reserve. No retry API, retry queue or automatic ZIP worker.
- All application containers run with a private leased TMPDIR/TEMP/TMP under `app/temporary/scratch/<service>/<operation_uuid>/`. Native FFmpeg/ffprobe unnamed files use explicit typed scratch, close with the operation and are measurable through open fds (not pathname scans). Atomic metadata/NPY/WebP writes stage there as well, then same-mount replace. Existing typed conversion, frames, FO staging and upload parts keep their authoritative task/DB lifetime rules. Scratch and download operations hold kernel directory leases; normal finally removes the directory, crashed unlocked directories become eligible after 3600 seconds. Unknown names are preserved. No separate preview-fragment sweeper.
- MegaLoc permanent bundle: `app/models/megaloc/weights/<weight_sha256>/model.safetensors`, `source/<source_revision>/`, and `metadata/current.json`. Official gberton/MegaLoc weights revision a0f34722c4297ff787e022433799250180860af7, SHA-256 d4f9f2bcb60018f91eb6a8e061ed054fd55654e10c2569cf13841ea986ffb4f8; official source gmberton/MegaLoc revision 5fe0dd697c4a70ba3e23607f6716ab3c606b16db. Explicit install downloads into a leased `app/temporary/model-downloads/<task_uuid>/`, verifies pinned Git blob digests and full weight hash, actually loads the checkpoint and runs finite 8448-dimensional inference, publishes source and weights before the atomic verified marker. Runtime refuses an unverified bundle and does not fall back to Torch Hub or Hugging Face. A valid existing bundle is never redownloaded on restart/reinstall; a damaged committed bundle requires explicit repair. No general model-upgrade UI or automatic destructive replacement is added.
- Only the three provider roots `app/cache/torch`, `app/cache/huggingface`, `app/cache/xdg` are proven disposable for the pinned bundle. Explicit offline maintenance via `app.system.technical_cache.clear_disposable()` requires a verified independent bundle and exclusive runtime guard with all application processes stopped. Not a periodic cache TTL. All shared reference objects/embeddings/thumbnails, owner previews, models and PostgreSQL state remain outside the purge. Recreated empty provider folders are normal.
- Mandatory CI docker-runtime acceptance uses original remote assets with pinned digests and two real public JPEGs, actual reference preparation, FO processing, Docker internal network without internet and separate --network none inference before/after provider purge, new processes, repeated FO and exact reference embedding cache-hit checks. Protocol-only fixture tests inject download interruption, insufficient disk, invalid hash and verifier failure; these never replace the real-model test. Full physical accounting and infrastructure/log relocation remain stages 7 and 6 respectively.


## Stage 6 infrastructure and journal policy
- A clean installation creates protected PostgreSQL 17 Alpine data (UID/GID 70) and Caddy data/config (root) in `storage/infrastructure`. Caddyfile remains a versioned deployment template; its writable native config and keys persist under the separate binds. API and workers cannot mount PGDATA, TLS private keys or root updater workspace. PostgreSQL is reachable only on the private Docker network. No legacy volume migration.
- All four application roles use one revision-labelled image, read-only rootfs, bounded 64 MiB /tmp and 32 MiB /var/tmp, managed app scratch, bounded 2 MiB x2 Docker fallback logs. Native PostgreSQL and Caddy are not subject to the app read-only rootfs.
- Main logs use the machine-readable budgets (MiB): api 50, worker 100, cleanup 30, thumbnail 30, Caddy access 100/runtime 30, PostgreSQL 100, processing 512 aggregate/20 per run, models 30, updater 50, audit 100. App and host JSONL use one active and four rotated segments; Caddy native file writers use 20/6 MiB and four retained segments, with URI/headers excluded. PG uses native collector rotation at 10 MB or 60 min and host pruning of closed logs only. No log statement/body capture, API access duplication or Docker socket access. Per-run cursor API remains on the managed processing log path. Budgets are operational targets, not hard FS quotas; active segment and asynchronous compression/GC may temporarily overshoot. Host maintenance exports a bounded metadata-only journal budget summary through the existing read-only control bind.
- Root-only update-branch pin is exactly feature/storage-architecture-v2 on this experimental branch. Current main remains unchanged. Restricted Unix socket status/check/update, trusted repo, clean tracked state and fast-forward SHA checks remain mandatory. Source tar workspace, protected pg_dump/config backups, builder markers, stable maintenance lock and status are all in storage/system. Candidate build is isolated; preserve current and previous revision tags, no force removal, no global prune. Root maintenance and installer/update share the deployment lock; only abandoned marked builders and recognized updater scratch are reclaimed. Failed transitions keep the maintenance marker and backup, never auto-restore over PG.
- Snapshot schema 3 includes user/reference/model persistent storage, resumable upload parts, protected installation metadata and native Caddy state. It excludes reproducible temporary archives/scratch/processing and logs. Logical PG dump instead of copying live PGDATA. Independent backup destination, checksum manifest, same-scope hardlinks and safe model symlinks; isolated staging DB and directory only. Root can use local Compose client transport (MAP_SNAPSHOT_COMPOSE_PG=1, postgres/sorter or sorter_restore_*); no public PostgreSQL port.
- No always-running global observer is installed. Optional bounded host diagnostic (60s/100k entries, 32 MiB per report), latest report only, plus explicitly started bounded live observation (60s/90 MiB). Neither is the authoritative accounting engine. Full accounting/reconciliation remains stage 7; no quotas.
