# Этап 4 — единая очередь, импорт образцов, уведомления, приёмка

Версия кода Stage 4 для `chapaayy/Sorter/main`. Только реализация, **не разрешение на VPS-деплой**.

## Что подключено

1. `/queue` — единая вкладка с FIFO `work_queue.seq`: ФО и подготовка образцов, тип, хронология, фактическое время выполнения, статус, готово N/M, ошибки, retry/stop/skip с отдельным подтверждением. Секция «Обработка» показывает Worker/настройки/текущий запуск и историю ФО, без параллельного списка очереди.
2. `/references` — загрузка и подготовка различены: дата/номер опубликованной версии, количество опубликованных образцов, последние import sessions, готово N/M, статус ожидания подготовки. Существующие формы импорта и добавления отдельных фото используют единый composable `useReferenceTransfer`, который в режиме Stage 4 выбирает `useStagedReferenceTransfer`. Сохраняются строгие названия папок и проверки сервера.
3. Staged transfer: регистрация всех файлов + SHA-256 и стабильные UUID, хранение ключа сессии в localStorage **только для восстановления после refresh**. Источник истины — серверный manifest; браузер после повторного выбора папки проверяет SHA, текущие offsets и докачивает остаток блоками до 16 MiB. Совпадения подтверждаются backend. Изображения до подготовки не видны распознаванию.
4. Уведомления в `/fo`: при открытии новой загрузки **GET** читает общий PostgreSQL cursor, не отмечая предупреждение прочитанным. После смены recognition-ревизии показывается одно сообщение, кнопка «Что изменилось» раскрывает реальные события, «Понятно» отдельно отправляет POST ack. Перезагрузка сайта/смена браузера не создаёт повторного уведомления после ack. Без первой завершённой ФО нет ложных предупреждений; path-only `baseline_immutable` и смена адреса не считаются recognition change.

## Feature flags

`PHOTOSORTER_UNIFIED_QUEUE=1` включает новую FIFO. `REFERENCE_IMPORT_STAGING_ENABLED=1` разрешает новый импортер только вместе с первой настройкой. Обе передаются **одинаково в api/worker/cleanup** через общий блок `app_env` в compose и по умолчанию имеют `0`.

При `0` сохраняется прежняя загрузка, старая остановка по активным заданиям и прежний worker. Новая вкладка показывает ledger, но сообщает, что режим пока не включён; UI не делает ложных утверждений о подготовке. Запуск новой загрузки образцов параллельно ФО разрешается интерфейсом только когда серверные флаги подтверждены.

## Новый PostgreSQL след

`0016_library_notice_delivery.sql`: таблица `fo_library_upload_receipts`, уникальный receipt на каждую завершённую партию, связанный с `reference_library_versions`. Существующая `library_notice_cursors(scope_key)` используется с ключом `installation`; можно расширить до будущего actor scope без новой авторизации. Запись receipt и обновление cursor происходят **в той же SQL-транзакции**, что успешная проверка полного FO manifest.

Первый успешный FO manifest запоминает базовую версию и не генерирует уведомление об изменениях до первой ФО. Следующие завершения не стирают неотмеченные изменения. Ack идемпотентен и монотонен: старый ack не скрывает новую публикацию.

События: `reference_prepared` и `legacy_reconcile` учитываются как изменения распознавания; `baseline_immutable` и изменение только адреса — нет. На будущее: при добавлении новых event_kind необходимо отдельно решить, влияет ли событие на распознавание.

## HTTP API

- `GET /api/reference-library/status` — опубликованная версия, дата, режим, notice и число непрочитанных изменений.
- `GET /api/reference-library/events?limit=30&after_version=...` — история публикаций.
- `POST /api/reference-library/notices/ack` `{"version_id": 13}` — *только явное* подтверждение.
- `GET /api/work-queue?scope=active|history|all&limit=...&offset=...` — единая очередь, позиция `seq`, текущие и исторические задачи.
- `GET /api/reference-imports?limit=...&offset=...` — последние staging-сессии и прогресс (только когда режим активирован).
- `GET /api/reference-preparations/{job_id}`; `POST .../retry`, `.../skip`, `.../stop` — отдельные действия по подготовке с контролем серверного состояния.

Старые API ФО, результатов, загрузки фото и библиотечного просмотра сохраняются.

## Проверки до VPS-развёртывания

- ФО×5 → подготовка×1 → ФО×1; убедиться, что версии первых 5 и последнего соответствуют моменту фактического запуска.
- Загрузить 545+ настоящих образцов, проверить точно N файлов, 2 параллельные сессии, потерю VPN на предпоследнем файле, refresh, crash API и recovery Worker; убедиться в ровно одном prep job на завершённую сессию.
- Неуспешная подготовка блокирует следующие ФО; нажать retry или явный skip (с подтверждением) и убедиться, что не возникла полуготовая библиотека.
- После прошлой завершённой ФО опубликовать новую версию; открыть новую загрузку — одно предупреждение. Посмотреть события, нажать ack, обновить страницу/другой браузер — больше не показывать; следующая публикация — новое предупреждение. Только дубли, адрес и технические копии не должны предупреждать.
- Chromium/WebKit desktop/mobile, управление клавиатурой, чтение статусов и контраст в тёмной/светлой теме.
- Сравнить настоящую сортировку 189 ФО против известного baseline **на одном наборе эталонов и версии модели**, а также провести 1315 ФО/массовый импорт с измеренными CPU/RAM/диском. Моковые CI-тесты этого не доказывают.

## Развёртывание и откат

**Ничего не разворачивать без отдельного разрешения владельца.** Перед переключением нужны offsite backup и проверенный restore БД PostgreSQL 17 + `PhotoSorter/data/` (включая `reference_objects`, `reference_staging`, cache, uploads/results) + `Models/` + `.env.generated` + Caddy TLS volumes. Сохранить предыдущий работающий commit. Не делать `docker compose down -v`, не вычищать `PhotoSorter/data`.

При проблеме с включённой очередью сперва остановить новые upload/dispatch. **Не переключать старый Worker просто выставлением 0, пока есть новые prep jobs или зависимые queued FO**: требуется согласованное восстановление через staging/backup и безопасное решение оператора. Планировать окно работ. Отдельный релизный приказ владельца обязателен.

## Что не проверяется CI

Реальные данные и VPS, реальный offsite восстановленный архив, 189/1315 ФО, реальное время подготовки 545 образцов, iOS Safari на физическом устройстве, стабильность бесперебойной сети, длительное хранение staging/объектов. Изменение маршрутов не означает активного production-перевода.
